# 観測（trace）と依頼の契約 — 「対策しても毎回間違える」を止める（2026-11-21）

## 今回の前提

| 項目 | 内容 |
|---|---|
| 課題 | ①Akira→エンジニアの依頼が落ちる（2項目のうち2番が報告からも消えた） ②対策しても同種の失敗が再発し、原因分析が当たっていない疑い |
| 実測（11-21 のラン） | 依頼#1: ツール**83回**/51.9円、依頼#2（「最小スコープ」）: **82回**/48.9円。**指示・応答の記録は0件** |
| 結論 | 失敗の原因は「意思疎通」ではなく**契約の不在**。そして分析の入力（ログ）が欠けていた |
| 方針 | プロンプトに書かず、**コードで強制**する（11-15 以来の一貫した結論） |

## 1. 記録（trace）

### 1-1. なぜ必要か（実測した3つの穴）

| 穴 | 実測 |
|---|---|
| 指示・応答が**1件も残っていない** | `_debug_log_io` は `logger.debug`、logger は `INFO` → 当日のログで `Akira本体] 指示` は **0件** |
| ツールの**引数と結果**が無い | 残るのは `Tool #N: name` だけ。「何を grep し、何を書いたか」が不明 |
| **突合キーが無い** | DynamoDB の費用・S3 の成果物・CloudWatch のイベントを結ぶ `run_id` / `item_id` が存在しない |

### 1-2. 何を残すか

| 保存先 | 中身 |
|---|---|
| DynamoDB `akira-trace` | `pk = run#<date>#<run_id>`, `sk = <seq:05d>#<kind>`、TTL **120日**、PAY_PER_REQUEST |
| S3 `akira-workspace/trace/<date>/<run_id>/<seq>-<kind>.json` | 本文（依頼文・応答・ミッション）。**無制限・非公開**。Dynamo には digest とキーだけ |

| kind | 内容 |
|---|---|
| `run.start` / `run.end` | 予算・実行時間・項目数・未達数 |
| `mission.built` | その日のミッション全文（企画候補・見張り・監査・鮮度） |
| `prompt.system` | **エージェントに渡した最終系のシステムプロンプト全文**（lessons・skills・SITE_RULES・site_plan・okamoコメントを合成した後） |
| `delegate.request` / `delegate.result` | 依頼文・応答全文＋**ツールの内訳（名前/回数/秒/エラー）**＋費用 |
| `item.status` | 作業項目ごとの達成・未達・未確認 |
| `gate.result` / `publish` | 公開ゲートの結果・公開ファイル・実URL照合 |

- **プロンプト全文を残す理由**: プロンプト自体が間違っていることがある（節約ノートの
  「40回に近づいたら持ち越し」が、まさに依頼項目を削る口実になっていた）。全文が無いと
  「なぜその判断をしたか」を後から検証できない
- 失敗しても本処理は止めない（記録の例外で日次が死んでは本末転倒）。Dynamo 不達でも
  例外を投げないことをテストで固定
- 伏字（`sk-` / `AIza` / `gh*_` / `AKIA` / Bearer / 秘密鍵 / `password=`）は記録時と
  公開時の**二重**でかける

## 2. 依頼の契約（1依頼1項目・受領書）

| 仕組み | 中身 | なぜ |
|---|---|---|
| **1依頼1項目** | `ask_claude_engineer(request, item_id, accept)`。依頼文に番号付き項目が2つ以上あると**ハーネスが拒否**（何も実行しない） | 2項目渡すと2番目が落ちる。判断に任せない |
| **accept（合格条件）** | 「labs セクション内の lab-card が8枚」のような**数えられる条件**を必須にする | 11-21 は「見出しを作った」が合格になっていた（構造の後退を誰も見ていない） |
| **DONE / NOT_DONE** | 応答の最後に `DONE: <item_id>` / `NOT_DONE: <item_id>`。無ければ**ハーネスが未確認**として記録 | 「やった」の申告に依存しない |
| **受領書** | 日報の末尾に**機械が**表を追記（達成/未達/未確認＋合格条件＋根拠）。フォールバック日報にも付く | 11-21 に2番が報告から消えた。書かなければ存在しないことになる構造を壊す |
| **publish_and_verify** | 描画→ゲート→公開→invalidation→**実URL照合**を1呼び出し | 83回の儀式を減らし、「残り呼び出し数」で依頼を削る口実を無くす |

## 5. 公開（オープンデータ）にする場合の設計と機密

### 5-1. まず「生の表を公開しない」

| リスク | 中身 | 対策 |
|---|---|---|
| 鍵の混入 | モデルが鍵を復唱する／ツール引数に載る | 記録時＋公開時の**二重伏字**。`trace_store.REDACT` と `publish_trace.REDACT` |
| 第三者の著作物 | `fetch_quote`/Firecrawl が取ったページ本文 | **本文はS3に置き、公開スナップショットには digest と文字数だけ**。`cache/` を公開しない既存方針と同じ線 |
| 個人情報 | okamoコメント・問い合わせ | メールアドレスを伏字。人の発言は公開 allowlist から外す（`report.claim` は文字数のみ） |
| 内部情報 | 費用・予算・S3キー・ARN | 費用は日報で既に公開済みの方針に合わせて数値のみ。S3キー・ARNは**出さない**（allowlist 方式） |
| 悪用・費用 | 生APIを公開すると誰でも任意runを引ける | **静的スナップショット**（JSONL）だけ公開。Dynamo は非公開のまま |
| プロンプトの内部事情 | サイトの課題・okamoとのやり取り | ここは**公開する前提で書く**（日報もリポジトリも公開済み）。書けない情報はプロンプトに入れない運用にする |

### 5-2. 推奨する形

```
akira-trace (DynamoDB, 非公開, TTL120日)
   └─ scripts/publish_trace.py --date YYYY-MM-DD --out s3://<公開バケット>/trace/YYYY-MM-DD.jsonl
        * allowlist の kind のみ / 二重伏字 / S3キー・ARN・ttl・pk は落とす
   └─ CloudFront で配信（1日1ファイル・immutable・CORS GET）
```

- **公開用バケットは別に作る**（ワークスペースバケットを公開しない）。バケット公開＋
  CloudFront は okamo の判断が要るため、いまは**スクリプトとスキーマだけ用意**している
- 1日1ファイル・JSONL・追記のみなので、API を建てる必要がない（費用0・悪用の余地小）
- `--include-bodies` は**内部調査専用**。付けた出力は公開しない（スクリプトが警告を出す）

### 5-3. いま公開してよいかの判断

| 項目 | 判断 |
|---|---|
| システムプロンプト全文 | **公開可**（リポジトリと日報で既に公開している内容＋合成後の中身）。むしろ「プロンプトがおかしい」を外から指摘できる利点が大きい |
| 依頼文・応答文 | 公開可（ただし本文はS3非公開・公開版はdigestのみ）。まずは digest のみで開始し、問題が無ければ本文公開へ |
| ツール内訳（名前・回数） | 公開可 |
| 取得した第三者ページ本文 | **公開しない** |
| 日報本文・okamoコメント | 日報は既に公開。コメントは元から非公開なので**trace にも入れない**（allowlist 外） |

## 8. 記録とプロンプトの棚卸し（2026-11-21 第3ラン）

### 8-1. Dynamo の項目サイズ（400KB）に当たらないようにした

心配していた「ツールの入出力が大きすぎて記録が溢れる」は、**入出力そのものは S3 に置き、
Dynamo には `key`/`digest`/`chars` だけ**を残す作りなので、通常は起きない。ただし次の2つは
実際に危なかった。

| 危険 | 実測・対処 |
|---|---|
| 入れ子の dict/リストが深いと `_ddb_value` の上限（60要素×深さ4）で**1項目が数百KB**になり得る | 項目を作ったあと `_MAX_ITEM_BYTES=180,000` を超えていたら `_spill()` が重い順に S3 へ逃がし、それでも超えるなら大きい入れ子を落として `dropped` に残す |
| `prompt.system` は「全文を残す」と書いてあったが、実際は汎用の文字列上限 **2000字で切れていた**（気づかないまま5分の1しか残らない） | `event(keep_full=("system_prompt",))` でその項目だけ上限を外し、大きすぎるときは S3 へ退避（`system_prompt_key`）。**切り詰めない** |

実測: 40万字（1.2MB）のプロンプトを渡しても、Dynamo の項目は **397バイト**、全文は S3 に
1,200,000バイトで保存され、`chars=400000` が残る。2万字のプロンプトは項目に**全文**が入る。

### 8-2. 日報の曜日（JST）

本文の先頭に「2026-11-21（金）日報 — LLM Data Hub」が入っていた。①ページ側の
`日報 YYYY-MM-DD` と重複 ②2026-11-21 は**土曜** ③サイト名の接尾辞が日報に付く、の3つが
同時に起きたもの。曜日はモデルに推測させず、**JST で機械が決める**ようにした。

- ミッションの冒頭を `今日は {today}（{weekday}）です` に（`jst_weekday_label()`）
- `write_daily_report` が本文を受けた時点で `_normalize_report_body()` を通す
  （先頭の日報タイトル行を落とす／本文中の `YYYY-MM-DD（曜）` を JST の正しい値に直す）
- 公開済みの 2026-11-21 の日報も同じ関数で直して再公開（`（金）` は0件になった）
