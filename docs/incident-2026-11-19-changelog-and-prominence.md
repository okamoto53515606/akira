# 更新履歴の反映・ページの見せ方・キービジュアル（2026-11-19）

## 今回の前提

| 項目 | 値 |
|---|---|
| 指摘者 | okamo（公開サイトを目視・11-19 の自動ラン後） |
| 対象 | `/changelog/`・`/mai/`・`/china-ai/`・`/timeline/`（いずれも日英） |
| 発見 | 公開後。**既存の7ゲートはすべて ERROR 0** で通っていた |
| 実行 | 2026-11-19 06:20〜07:00 JST（S3＋CloudFront invalidation `/*`＋ECRイメージ） |

## 何が起きていたか

| # | 指摘 | 実際に起きていたこと |
|---|---|---|
| 1 | 更新しているのに `/changelog/` に反映されない | 11-17 に「反映されすぎる」を直した際、`site_events` への自動登録を**新規ページだけ**に絞った。その結果、**既存ページの更新は1件も履歴に載らない**状態になっていた |
| 2 | `/mai/` が「2026年10月版」のまま。MAI Code 2 を足したのに目立たない。年表にも無い | 本文の**末尾に段落を1つ足しただけ**で、見出し・表・年表に入っていない。タイトル・見出し・description の年月表記も10月のまま。9〜10月の行に `New` バッジが残っていた |
| 3 | `/china-ai/` の Qwen4-Max が目立たない。古い情報の方が目立つ | Qwen のカードは**旧フラッグシップ（Qwen3.8-Max）から始まり**、Qwen4-Max は2段落目。比較表も 3.8-Max が先 |
| 4 | `/timeline/` のメイン画像が「〜2026年10月」のまま | この画像は `og_specs.json` に**登録されていなかった**ため、R5（画像が本文より古い）の検査対象外だった。描画は過去の単発スクリプトの産物で、本文と機械的につながっていない |

## 原因

- **更新履歴**: `_register_site_event(is_new=...)` が新規ページだけを対象にしていた。既存ページの更新を拾う経路が無く、「更新したら履歴に載っていること」を検査するゲートも無かった。
- **ページの見せ方**: 生成側（エンジニア）の判断に委ねられており、機械の検査は「追記バナー」「日付で始まる見出し」「同じ指標の複数値」までしか見ていなかった。**「新しい情報が見出し・表・年表にあるか」**は検査対象外だった。
- **監査の対象**: `pick_targets` は `page_priority.json` の10ページからしか選ばず、1ラン2ページ。**`/mai/` は優先度リストに入っていないため永久に対象外**だった。さらに `_page_meta` が `class="updated-bar"` の直後が `>` であることを前提にしていたため、**`style=` が付いたバーを読めず R1 が素通り**していた。
- **キービジュアル**: `og_specs.json` に無いページは R5 の検査対象外（＝仕様が無いこと自体が検出されない）。
- **日付ゲート**: description の「（2026年10月更新）」は「〜日更新」の形ではないため `check_dates` が読んでいなかった。

## いまの設計

### 1. 更新履歴は「中身が変わったか」で自動的に載る（`tools.py`）

公開時に、S3 にある**現在の公開版**と**今回アップロードする実物**の指紋を比べる。指紋は
`updated-bar` / `dateModified` / `<time>` / `?v=` / sitemap lastmod を潰してから取るので、
**日付だけ新しくした更新では履歴に載らない**（11-17 の「32ページが本日公開で埋まる」を再発させない）。

- 変化があれば `site_events` に `kind: "update"` を1件足し、**その場でトップ・`/changelog/`・sitemap を描き直して公開**する
- 文面は見出しの差分から作る（例: 「…を更新 — 見出し「最新モデル（2026年11月）」を追加」）
- 同じ日に同じページの履歴が既にあれば足さない。8ページを超える更新は1件にまとめる（水増し防止）
- 1ページだけの更新でも大量更新でも、履歴と実物が同じランで揃う

### 2. 「古いのに新しいフリ」を公開ゲートで止める（`page_audit.py` / `tools.py`）

`site_upload` が、アップロード**前**の実物にページ監査を当てる。止めるのは
**今回の公開で新しく出た ERROR だけ**（既存の借金で作業が止まらないように）。
例外として R4/R9（見出し・タイトルの年月が古い）は、**dateModified を進めた公開**なら既存でも止める
＝「日付だけ新しくして中身が古いまま」は通さない。

| ルール | 見るもの | 公開を止める |
|---|---|---|
| R1 | 「最終更新」の表示と JSON-LD の食い違い（`style=` 付きのバーも読む） | ○ |
| R2 | 追記バナー（`2026-11-12 追記:` 等） | ○ |
| R3 | 同じ行ラベルに違う**金額**（分類表・USD/JPY の別表は誤検知しない） | ○ |
| R4 / R9 | 見出し・タイトルの年月が最終更新より古い（「2026年10月版」「最新モデル（2026年10月）」） | ○ |
| R5 | キービジュアルの生成日が本文より古い | ○ |
| R6 | 日付で始まる見出し | ○ |
| R8 | 同じ指標に複数の値（版番号・別名の指標は誤検知しない） | ○ |
| R10 | 台帳の新しいモデルが、そのページの年表に無い | ○ |
| R10b | 見出しに書いたモデルが、そのページの年表に無い | ○ |
| R11 | 台帳が本文を持つ特集ページで、新しいモデルが本文の段落にしか無い | ○ |
| R5b | キービジュアルがあるのに `og_specs.json` に仕様が無い | WARN（移行途中） |
| R7 | 「取得日」が最終更新より30日以上古い | WARN |

### 3. 触ったページは次のランで必ず監査する（`page_audit.py`）

`site_upload` が、公開した `index.html` を `data/page_audit.json` の `pending` に積む。
`pick_targets` は pending を**先頭に**入れて割り当てる（監査したら外れる）。
優先度リストに無いページ（`/mai/` など）でも、更新した翌ランには必ず見る。

### 4. キービジュアルは台帳のデータから描く（`og_card.py` / `data/og_specs.json`）

`/timeline/`・`/mai/`（日英）を `og_specs.json` に登録し、`og_card.py` で描き直した。
画像の文面は `facts`（箇条書き）として台帳にあり、`generated` がページの dateModified より古いと R5 が ERROR にする。
長い箇条書きが下の URL と重なる問題も直した（収まるまで自動で字を縮める）。

### 5. レビューの観点（`prompts.py`）

- Gemini子育てママ **S11**: 新しいモデルが見出し・表・年表にあるか／古いモデルが先頭で最新に見えないか
- Gemini子育てママ **S12**: 本文と年表の一致、タイトルの年月が古くないか
- GPT税理士: 「同じページ内の食い違い（年表に無い・年月が古い・段落にしかない）」は**クリティカル**
- Claudeエンジニア: 「新しい事実は見出し・表・年表に置く」手順を明記

### 6. 日付ゲート（`tools/check_dates.py`）

description の「（2026年10月更新）」のような**年月だけ**の更新表現も、宣言日付と突き合わせる
（同じ月なら合格、**月が古い**ときだけ NG）。

## 前提が変わったときの要注意事項

| 前提 | 崩れたときに効かなくなるもの |
|---|---|
| ページの中身は `facts.json`（features / models / pricing_tables）が正で、HTML は描画される | 指紋は**公開物のHTML**を見るので、描画を経ない手編集も「更新」として履歴に載る。台帳に無い事実を HTML にだけ書くと次の描画で消える |
| 監査は「新しく出た ERROR だけ」止める | 既存の借り（いまは追記バナー6件）を放置すると、その**ページは直すまで公開できない**状態が続く |
| R11 の対象は `features.<slug>` を持つ特集ページ | 特集ページ以外（個別モデル・用語集）で同じ失敗が起きても機械は止めない。S11/S12（Gemini）と GPT のクリティカル判定が受け持つ |
| キービジュアルは `og_specs.json` に仕様がある前提で R5 が効く | 仕様の無いページは R5b（WARN）にしか出ない。画像を足したら**同じランで specs に登録**する |
| `page_audit.json` の `pending` は最大40件 | 大量更新が続くと古い pending が押し出される。その場合は優先度リスト側で拾う |
| 履歴の自動登録は「公開物の差分」で判定する | 生成物（ロゴ・CSS など）を触っただけでも、そのページの履歴に「本文を更新」が載り得る。文面が具体的になるのは見出し差分があるときだけ |
