Batch API discounts compared (November 2026)

What a Batch API is: you submit a large volume of requests asynchronously and collect the results later. You give up real-time latency, and the per-token price drops to roughly 50-60% of standard.

How far the per-token price drops when you send a large volume of requests asynchronously, in one table. You trade real-time latency for a lower rate, so "can this job wait?" is the deciding question. Standard rates live in the LLM API pricing comparison; reuse of the same prefix is covered in prompt caching rates compared.

●Last updated: November 12, 2026 | Official pages fetched on 2026-11-12; quotations are verbatim. Amounts derived by applying a published discount to a standard rate are labelled "calculated".

Three things to know first

  • The big three all sit at 50% off. OpenAI, Anthropic and Google each halve the standard rate. The discount alone does not separate them, so deadlines, retention and caps do.
  • Some providers set the discount per model. xAI varies by model and gives no discount to models outside its table. Moonshot charges 60% of standard, which is shallower than a 50% cut.
  • Batch stacks with caching. Anthropic states verbatim: "Batch API and prompt caching discounts can be combined." For a nightly job that reuses the same instructions, cache plus batch is the cheapest combination.

When it pays off: a nightly classification job

Say you classify 200,000 support tickets overnight into issue types. At 1,500 input tokens and 200 output tokens per ticket, that is 300M input tokens and 40M output tokens.

ModelStandard APIBatchDifference
GPT-6.1 Terra ($1.00 / $5.00)$300 + $200 = $500$250-$250
Gemini 4 Argon ($2.00 / $10.00)$600 + $400 = $1,000$500-$500
Kimi K3.1 Pro ($2.00 / $10.00)$600 + $400 = $1,000$600 (60% of standard)-$400

The job only needs the results by the next morning, so it fits inside the batch window (mostly 24 hours). A moderation check that has to answer on screen in the same request cannot wait, so it stays on the standard API. In practice: daily aggregation, classification, extraction and embedding jobs are batch candidates, while conversational loops and agents are not.

If every request carries the same prefix (instructions, category definitions), combine this with prompt caching to cut the input side further. Anthropic explicitly allows the combination; OpenAI and Google treat caching and batch as separate discount axes (check each provider's docs for the order of application).

Batch is a latency and deadline trade-off

Batch APIs are asynchronous: you submit a job, get an ID, and collect results later. OpenAI states "Each batch completes within 24 hours (and often more quickly)" and the completion window can only be set to 24h. Google states "The target turnaround time is 24 hours, but in majority of cases, it is much quicker." xAI says batch requests are "queued and processed in the background, with most completing within 24 hours". The docs state an upper bound ("within 24 hours"); they do not say when inside that window a batch will finish. For business-day use, submit the night before and collect in the morning.

Expired requests are handled differently too. OpenAI writes them to an error file (code batch_expired), so you receive the successful subset only, which means designing for partial results and reruns. Rate limits also differ: xAI notes batch requests "don't count towards rate limits". Cheaper, but you own the deadline, partial-failure and collection logic.

Retention can be short. OpenAI states "The output file will automatically be deleted 30 days after the batch is complete." Copy results into your own storage as soon as a batch finishes. Retention for the other providers is shown as "Not confirmed" in the table above and will be added when we can quote it.
